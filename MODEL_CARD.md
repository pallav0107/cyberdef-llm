## Intended use — DEFENSIVE security only

A blue-team assistant that, given a single code snippet, judges whether it contains a
security vulnerability (`VERDICT: VULNERABLE` / `SAFE`, plus a CWE name when applicable).
Intended for secure-code review, triage support, and research into whether small open
models can assist defenders.

### Out of scope / prohibited

This model is **not** for generating exploits, malware, attack payloads, or any offensive
capability. It is a classifier of given code, not a generator of attacks. Do not use its
output as the sole gate on whether code is safe to ship — it is an assistant, not an
authority, and (see Limitations) it is near chance on real-world C code.

## Training data

- **Increment 1 (synthetic):** a ground-truth-by-construction suite of labelled
  vulnerable/safe snippets across 8 families (sql, cmd, path, hash, secret, deser, eval,
  xss), with 2 families (ssrf, token) withheld from training. No model-generated labels;
  no outputs of any commercial API were used as training data.
- **Increment 2 (real):** the **CodeXGLUE Defect Detection** dataset (the Devign corpus;
  real C functions from FFmpeg/QEMU, MIT-licensed redistribution). Trained on the TRAIN
  split only, with every function whose normalised text also appears in the validation or
  test split removed, so the reported test numbers cannot be inflated by duplicates.

- **Increment 3 (real, the released champion):** the **PrimeVul** dataset (`colin/PrimeVul`; curated, lower-noise vulnerability labels). Trained on the TRAIN split only, leakage-deduped against the 48,736 validation/test functions. This is the adapter (`out/qlora-primevul`) behind the headline leaderboard result; the same recipe was also applied at 1.5B and 14B for the scaling table. No model-generated or commercial-API outputs were used as training data at any size.

## Limitations (read before trusting any number)

- On the recognized **Devign** benchmark, general instruct LLMs — including this one — sit
  **near the 50% chance floor**. The synthetic-trained adapter *reduced* accuracy there by
  making the model answer SAFE far more often. A high in-distribution score is **not**
  evidence of real-world vulnerability-detection skill.
- Devign's function-level labels are known to be noisy (one motivation for the later
  PrimeVul dataset). Treat absolute accuracies with that caution; the baseline-vs-tuned
  **delta under an identical prompt** is the honest signal, not the absolute number.
- Inputs are truncated (default 4000 chars), so very long functions are judged on a prefix.

## Ethical considerations

Defensive scope only. The model should never be relied on as the sole arbiter of safety;
false "SAFE" verdicts are the dangerous failure mode and are frequent on real code.
